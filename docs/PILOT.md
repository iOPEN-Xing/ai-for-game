# 一款小游戏值得再做一版吗？（试点与经营口径 · v2.1）

> 位置：`docs/PILOT.md`｜用途：试点招募、报价与验收口径。需求基线见 `SRS.md` v2.1，当前工程验收见 `ACCEPTANCE.md`。**本文数字均为口径说明，不替代线上实测**——原案例数字按来源分别列出、不可相加（见 `original/01-全文整理.md` 附录 B）。
> 原图依据：`original/assets/img-03.jpg`（08 汇总：对端 +2.5%/+23.5%/+1.3%/+3%，迭代 +15.3%/+6.4%/+1.7%/+1.1%）、`img-45~img-50`（JellyGame 迭代提案界面与效果截图结构）、`img-56.jpg`（可证伪结算）、`img-06.png`（人只做北极星+审核）。

回路制作室面向有固定活动入口、需要反复投放小游戏的小团队。制作负责人要知道，本周该验收哪一版。活动运营要知道，玩家从哪里进来、在哪一步离开、改版后有没有更多人愿意打开活动页。这两个决定共用一套游戏版本和对局记录。

## 哪些技术值得迁移（每项落到验收动作）

| 原文中的技术点（原图） | 当前实现与取舍 | 对买方的作用 → 试点验收动作 |
| --- | --- | --- |
| 生产和运营分工，共享中间产物（img-06 L1–L5 / img-14） | AgentScope 接入 `glm-5.4`（当前基线，见 `../studio/settings.py`；原文案例时期模型版本不同，移植以当前配置为准）。策划、素材、关卡、代码及技能版本随制作版本保存。运营只能提案，审批后才能进入生产。SQLite 状态机管理中断、重试和返工 | 修改美术可保留已确认策划，验收人能追到本次修改与执行依据。**试点量交接次数与人工返工时长**（目标：返工定位到域，不整包重做） |
| 游戏宿主固定，玩法和关卡可替换（img-37/38 MF 三通道） | 浏览器宿主加载独立游戏包，用相同关卡配置处理试玩与发布。QuickJS 运行受约束二维逻辑；当前支持点触、路径、轨道及接口约束内自定义。原案例另有远程编码容器与独立素材服务（本项目 Phase-1 为单进程+QuickJS 等价实现，见 ADR-002） | 玩家入口可延续，运营可并行测两个不可变版本，失败回退。3D/任意引擎插件另行估价。**验收：同包双臂并行、回退 <5min** |
| 难度由算法、参数和种子决定（img-32 双模式） | 运行时生成（模式 A）与预制蓝图（模式 B）分别交付。构建检查多种子、胜利输入回放；路径解谜再由独立程序按蓝图逐格点击，发布模块须在对应终点通关 | "首关太难"与"地图走不通"分别处理。**验收：给 Seed 复现问题关；改参数后蓝图 diff 回归** |
| 数据按场域、游戏、关卡逐层拆分（img-55 整批门禁） | 正式入口绑定来源，报表保留游戏、版本及关卡。三级口径单一实现；冻结禁 V1 样本配 V2 源码。活动漏斗用浏览器玩家标识去重。自然完局需真实版本回放，验收试玩与内置样片单独处理 | 区分入口访问/开玩/完局/行动点击；入口差异为改版线索。**验收：任一结论可下钻到冻结快照（版本+构建+分母+源码行）** |
| 先写可证伪预测，再回收证据（img-56 三层归因） | 分析团队冻结观测窗、代码、原始反馈和入口数据。每日按该游戏主指标对照前七日基线排优先级。玩家固定分流 A/B，结算检查交付差异、样本门槛和外部变更。获准生效知识才进后续分析 | 客户可追问"为什么改、实际交付什么、依据够不够"。**验收：每条批准提案有预测区间+证伪条件+到期结算；样本不足标未验证、不强行全量** |

制作、分流和结算的源码入口见仓库中的 `docs/ARCHITECTURE.md`。优先级取主指标相对降幅，随后看样本量；有数据但无正值历史基线的项目按样本量候补。它决定分析顺序，效果归因由后续实验验证。

移动端交付也要计量。正式对局现在单独领取对局记录，游戏代码和素材按版本缓存。用现有样片《潮汐信标》验收时，旧式开局响应为 143,676 字节，新式为 986 字节。首次游玩另取 143,628 字节游戏包，进下一关浏览器为同一包传输 0 字节。这是一个版本的实测字节数，玩家等待时长与开局率仍需在真实网络下观察（包 ≤5MB 硬上限，SRS NFR-3）。

## 第一批客户与替代方案

首批试点对象可选品牌会员运营、内容社区或代运营团队，前提是同一团队能发布活动链接、安排第二次活动，并取得必要汇总结果。日常使用者是活动运营和制作人；预算负责人通常要看到活动效果与交付工时。**只有一次展示需求时，模板或外包交付已能解决大部问题**；已有游戏研发和埋点团队时，Unity 漏斗或 Firebase 实验能力也能独立承担分析。差异化要用"同一活动从发现问题到安全发布下一版"的时间与成本证明。[Unity 玩家漏斗](https://docs.unity.com/en-us/analytics/funnels/create-funnels) · [Firebase 实验方法](https://firebase.google.com/docs/ab-testing/ab-concepts)

| 情形 | 更合适的选择 | 本项目赢在哪才值得买 |
| --- | --- | --- |
| 一次性活动、无复用 | 模板/外包 | 赢不了，不建议试点 |
| 有研发+埋点团队、只缺实验 | Unity/Firebase 自建 | 赢在「改代码→发包→结算」闭环速度（3 天级），需实测 |
| 有流量、无研发、需反复投放 | **回路制作室试点** | 赢在「创意→可玩→回流→再迭代」全链路 + 每次迭代可审计 |

可先按单次活动及一次改版提供付费试点。报价前记录策划和审核工时、模型账单（`usage_ledger` 四类：Token/图/字节/流量）、素材成本、运行费用及支持工时。单活动贡献 = 实收试点费 − 直接成本。单款短游戏的生成价格、客户愿意付的价格和可持续毛利，需分别测量（Phase-1 先做到每单可对账，P7 再谈订阅）。

## 在制作台跑一次试点（5 步，含 DoD）

1. **定目标与基线**：运营写下目标人群、目标动作和限制。如社群活动希望更多访客主动打开活动页，选"活动入口点击率"，同时观察自然完局率作体验护栏。先保存上一场可比活动的人工工时、日历耗时和入口数据（无基线则首场只验交付、不验增量）。
2. **做一款可玩游戏**：从玩法草稿制作一款游戏，经方向、方案、试玩验收后发布。在"运营与实验 → 活动入口"按来源建链接（如"公众号菜单""社群内测"）。为同一业务目标设同样按钮和落地页，分别发布对应链接。
3. **读漏斗**：访客→开局看入口承诺与加载体验；开局→完局看版本与逐关数据；完局→行动看按钮与玩家刚完成的动作是否相关。不同来源人群自选进入，来源排行本身不能证明渠道效果（去重：每入口内按 `loop-player` 去重，跨入口汇总再去重；跨浏览器/清存储产生新标识，属已知误差）。
4. **开实验**：预先约定每组人数、实验时长、最小有意义提升和体验护栏。同一入口玩家稳定分流两版（同人同实验同臂；回访进度三策略预注册其一，SRS R-AB），保持投放、按钮与落地页一致。若换活动/渠道构成突变，在"外部变更"登记。到期先核实交付文件（参数原值=control 实值？）、人数和区间，再决定扩大/重做/回退。**DoD：交付≠预期 → 不结算为正向；样本不足 → `delta=null` 留未验证。**
5. **对账与复用**：客户用自有活动后台核对报名、核销或订单，并在第二次活动复用流程。一次漂亮演示只验证可操作性；**真实发放、形成一次有依据的改版决定、付费续做，才分别提供使用价值与商业需求的证据**。

## 指标怎样读

| 指标 | 分子与分母 | 能支持的决定 |
| --- | --- | --- |
| 开局率 | 去重开局玩家 / 去重访客 | 入口是否把目标人群带到开玩这一步 |
| 自然完局率 | 经回放确认的胜负局 / 全部开局；同一玩家可贡献多局 | 在哪个版本、哪一关检查中途离开和难度 |
| 活动入口点击率 | 点击行动按钮的去重玩家 / 从带按钮入口进入的去重玩家 | 这次游戏是否把更多访客带到活动页入口 |
| 单活动贡献、复用 | 实收 − 直接成本；第二次活动中实际复用并付费的团队数 | 是否值得扩大投放、做订阅或增加玩法 |

每个入口内部按浏览器玩家标识去重。一个玩家可出现在两个入口，汇总需重新去重。跨浏览器和清除本地存储会产生新标识。时间范围按对局进入时间归属，只纳入截止前收到的事件。自然完局后按钮才出现，主动退出不产生行动点击。站外订单、广告消耗、退款和跨设备身份，需客户系统提供。

点击率实验以每位可见该入口机制的访客为一个二元观察。系统计算实验组减对照组的百分点差和 Newcombe–Wilson 95% 区间。若整个区间都低于证伪阈值，可否定最低收益预期；其余情况（区间跨零或跨过阈值）保留不确定性。这个区间适用于独立玩家的二项比例；**以多局为分母的通关率不套用此区间**（局间相关，需按玩家聚合或声明口径）。把样本门槛写在实验前，并在预定到期时判断。[Newcombe 的两独立比例差方法](https://pubmed.ncbi.nlm.nih.gov/9595617/)

试点招募时先算所需流量。假设历史点击率 10%，客户认为 12% 才值得改版。按独立访客、两组等量、双侧 5% 显著性水平和 80% 检验功效的正态近似，每组约需 3,841 位可测访客。这是规划示例，实际门槛取决于客户基线和最小有意义提升。**只有几十名玩家的试点，仍可验证能否顺利交付、哪里卡住、客户是否愿意再买一次**——交付验证与效果验证分开计，不混为一谈。[两样本比例的功效计算](https://stat.ethz.ch/R-manual/R-devel/library/stats/html/power.prop.test.html)

## 下一笔投入如何决定

首轮试点可先与两三支已有流量团队各做一场，以一场可比活动为基线（数量为招募建议）。产品负责人应同时看：**上线耗时、人工净工时、点击率及其不确定性、贡献毛利、客户是否愿按相同条件再做一次**。若主要损耗在开发交接，优先改善返工和验收（FR-1.4 精确失效）；试玩顺利但活动后续行为弱，先调目标或落地页。若客户能复用、有正贡献且愿续费，再投客户系统订单回传、跨活动身份和多租户权限（SRS P6–P7）。现阶段尚无实客订单、因果收益或市场规模的实测结论——**本节所有数字都是决策框架，不是业绩承诺**。

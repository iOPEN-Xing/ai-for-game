# 小游戏生产与运营 Agent 工程审查（历史快照：修复前复现）

> 已归档，不代表现状。此文保留修复前的复现结果，仅作历史对照。当前实现、验收与剩余边界见[修复后的工程验收](ACCEPTANCE.md)。
> 快照基线：`GLM-5.3` / 16 项回归均为当时的记录；当前基线为 `glm-5.4` / 31 项回归，见 `ACCEPTANCE.md` 复核记录。

审查对象为当前工作区的生产、运营、游戏宿主与测试代码。以下七章对应本次提供的七张图。判断依据是数据实际传给了谁、程序允许什么状态转移、错误交付能否被拦住。本机使用 AgentScope 2.0.12，代码默认云模型为 GLM-5.3。以项目现有技术栈能否完成图中的业务任务作为验收口径。[模型与 Agent 构造](../studio/agents.py#L275) · [原文的全链路分工](original/03-原文全文.md#L80) · [原文的运营专家团](original/03-原文全文.md#L367)

**生产链可以交付并验证可玩的游戏。运营链已经具备独立首评、反方复审、主持人提案和人工批准，但尚未达到图中“专家解决关键分歧之后再送审”的要求。** 运营负责人作决定时，需要知道数据属于哪一版、反对意见如何处置，以及上线的改动能否验证原提案。回访玩家在 A/B 中进入不同起始关卡，还会给结果引入额外解释。

## 图 5　一个宿主加载多个游戏

**对当前小游戏范围，共享宿主的目标已实现。** 试玩页和正式游戏共用播放器，由宿主领取对局、查询配置、记录开始与结束、展示反馈。游戏模块通过 `init/get('./game')` 暴露状态、输入、绘制和关卡接口，在隔离页面的 Worker 内运行。正式资源按构建哈希缓存，每局另外领取记录。项目采用轻量模块协议，公共游戏辅助代码仍随各包打包，不能据此推定具备通用 Module Federation 的共享依赖版本协商。[播放器入口](../studio/web/play-host.js#L36) · [模块接口](../studio/cartridge.py#L237) · [Worker 装载](../studio/web/frame.html#L217) · [资源缓存](../app.py#L275)

**共享宿主中有一个影响实验的进度问题。** 两个玩家都已通关 V1 第一关。在只改计分、两版关卡一致的实验里，两人分别进入对照和实验组，默认落点是第 2 关和第 1 关。分流对同一玩家稳定，但进度查询同时按版本过滤，实验组同时经历了从首关重新开始的变化。相容版本可以迁移进度，不相容版本可以给两组设同一起点或把回访玩家单独分析。验收时应同时检查玩家的旧进度、实验分组和两组首个实际关卡。[稳定分组](../studio/operations.py#L274) · [解锁进度查询](../app.py#L516)

**已复现批准内容与实验交付错位。** 批准的唯一改动是把第一关时限增加 10 秒。测试中只改了 `game.js` 的命中计分，对照组与实验组的第一关均为 60 秒，实验仍进入 `running`。质量评审会收到批准提案，但程序只验证两个包存在可识别差异。应将这一类批准项保存成“版本、关卡、参数、原值、目标值、验证方式”，发布时直接读两份关卡包验收。玩法改动可以用给定输入的行为回放验收。这样实验结算才有依据把观测值归给被批准的改动。[交付差异范围](../studio/operations.py#L181) · [实验开闸条件](../studio/operations.py#L226) · [结算交付核对](../studio/operations.py#L433)

### 新游戏立项

项目可以从已上线游戏的数据发起立项。系统使用该游戏的指标和行动边界，人工批准后创建新游戏，首发后可以对账是否上线以及首次正式曝光。立项和迭代在审批后的去向不同，但在审批前实测均是相同的六次角色调用。生产调研的两三个玩法方向发生在立项获批之后，不能为之前的投资决定提供候选对照。[任务输入](../studio/operations.py#L298) · [角色调用顺序](../studio/operations.py#L330) · [批准后新建游戏](../studio/operations.py#L385) · [首次曝光对账](../studio/operations.py#L688)

对照图 7，立项应先锁定北极星并检索适用的失败经验。分析师提交约束，评审提交已知死路和口径审计，两份齐全再让设计师出两至三个候选。随后分析师逐项挑战，设计师回应。主持人保留一个推荐并记录其他候选的淘汰理由，由评审复核最终立项书的证据与重合风险，再送人审。当前知识检索可返回已生效的反面经验，但没有必读的死路清单。按游戏、日期、类型防重复提交，也无法识别换名重提的旧玩法。立项书记录预期上下界，首次曝光对账还不能判断它是否达到自己的预期。[知识检索](../studio/operations.py#L124) · [批次防重](../studio/operations.py#L105) · [首次发布的状态](../studio/operations.py#L258)

## 日报、自进化与经营验证

日报在北京时间 08:00 后处理上一自然日，每半小时巡检漏批、僵尸任务和已到期实验。程序会核对全局、游戏、关卡三级报表的开局总数。批次交付检查只要求已有主持人提案且状态不属于分析中或失败，因此现有巡检可以发现漏交文档，同样会放过本报告复现的未结争议。拆分运营流程后，日报、人工入口和断点恢复应复用同一份送审条件。[巡检与补跑](../studio/worker.py#L130) · [三级报表核对](../studio/operations.py#L656) · [批次交付检查](../studio/operations.py#L719)

隔离试玩与正式数据、截止观察窗、固定实验分组、预设样本门槛、结算时识别外部干扰，以及未验证知识不进入生效库，都有程序支撑。当前新知识经人工批准且归因为“假设错”时，会将该游戏中本次引用的所有生效旧知识标为失效。一次提案可能同时引用玩法假设和事实口径，证伪前者不应自动撤销后者。可以给每条知识记录它在假设中的用途，由审核人逐条确认哪些证据受到反驳。[冻结观察窗](../studio/operations.py#L43) · [样本与干扰判断](../studio/operations.py#L444) · [知识状态更新](../studio/operations.py#L582)

优先顺序建议按决策代价安排。先对齐版本、样本和起始进度，再让争议能退回补证，并要求实验精确验收批准项。随后拆分两类任务的手册与状态机，补入死路检索和立项终审。外部搜图和细粒度资产复用可以分别用调研命中率、返工耗时衡量。对首个客户试点，更有解释力的记录是每份获批提案能否定位到证据和实际改动、为此花了多少人工复核时间，以及客户是否愿意用同一套流程做第二次活动。此次审查没有验证客户收益或付费需求。[项目的试点与衡量口径](PILOT.md#L31)
